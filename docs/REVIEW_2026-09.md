# Architecture review, 2026-09-21

A read-only review of fizzy (working copy on top of bookmark `fizzy-lib`, SDK 0.2.0 unreleased),
the four out-of-tree plugins (`fizzyedit/{zig,ghostty,pixi,atlas}`), and the new cloud-fs work
(`fizzyedit/zig-drive` + `plugins/{archive,drive}`), against the idea fizzy is meant to be: a
near-empty native host that installs and updates itself and its plugins, reloads them live, and
can develop plugins for itself. Every finding was read in the code; line numbers are from the
working copy on the review date and will drift.

Gates on the review date: `zig build`, `zig build test`, `zig build check-web` (17/17),
`zig build test-sdk-version` all pass. `zig-drive`: `zig build test` + `check-wasm` pass. All
four out-of-tree plugins build against `../../fizzy/sdk` (18–26 s each, fingerprint
`0xfce7273c34e25eab`).

**Side effect of the review:** building the four plugins ran their default install step, which
copies the dylib into `~/Library/Application Support/fizzy/plugins/<id>/`. The installed copies
are now local-SDK builds, not store releases (see H-plugins §gaps, item 9).

---

## 1. The verdict in one paragraph

The essence is built and holds. The host owns no features; regions/keywords/surfaces made the
workbench's tab system a plugin-declared region without a special case; services are versioned
and multi-provider; the fingerprint gate, the stable-copy dylib loader, the store pipeline, the
watchers and the ZON settings surgery are each careful, documented answers to a real bug. What
is not finished is the *edges of the contract*: the fingerprint misses several by-slice types,
live unload can leave function pointers into a closed image, a handful of pixi/workbench-shaped
members still sit on `EditorAPI`, and the cloud-fs layer has a cluster of lifetime bugs in its
completion/cancel paths that the tests do not reach. None of it is structural. The strategic
question (web) has a better answer than expected: the desktop dylib model translates to wasm
dynamic linking almost unchanged, and it was demonstrated end-to-end under node during this
review.

## 2. Web strategy (the user's questions, answered)

### 2.1 Can a plugin be compiled to wasm and loaded at runtime? Yes, with today's toolchain.

Measured, not assumed. In the scratchpad, Zig 0.16 produced an Emscripten-style **side module**
from `zig build-lib side.zig -target wasm32-freestanding -dynamic -fPIC -fno-entry`: a
`dylink.0` section, imports for `env.memory`/`__indirect_function_table`/`__stack_pointer`/
`__memory_base`/`__table_base`, and an exported `__wasm_apply_data_relocs`. A main module built
with `--import-table` (the JS-owned table must be growable; `--export-table` emits `max ==
initial` and `table.grow` throws) and `--export=__stack_pointer` loaded it, applied relocations,
and **called a plugin function through a function pointer read out of relocated plugin data**.
Constraints found: `-fPIC` is mandatory (without it wasm-ld refuses `R_WASM_MEMORY_ADDR_LEB`);
it goes through LLD, which prints `creating shared libraries, with -shared, is not yet stable`.

Why the SDK boundary survives unchanged: the desktop design *already is* the MAIN/SIDE model —
host and plugin each compile their own `dvui`/`sdk`/`core`, the host injects pointers
(`sdk/src/dylib.zig:1-9`, `dvui_context.zig:16-33`), and the proxy dvui backend a plugin links
has **zero `env` function imports** (everything goes through `RenderBridge` fn pointers). On
wasm: vtable fn pointers become indices in the one shared table (`call_indirect` type-checks
them; same compiler ⇒ same signatures); data pointers and slices are offsets in shared linear
memory; `dvui.io`/`dvui.debug` copy by value with identical layout; the fingerprint is
target-invariant by design so it matches as long as the web host ships the store's
optimize class (ReleaseFast/Small); `threadlocal` collapses to a global because the web exe is
`single_threaded` (`build/web.zig:42`).

What stays impossible on the web regardless: **unload** (no `dlclose`; disable = hide), threads
inside plugins (no SharedArrayBuffer without COOP/COEP), processes (LSP, terminal, git), libc
(`wasm32-freestanding`), OS file access beyond picker/download.

### 2.2 Separate wasm instance per plugin (own memory)? No.

Everything crosses by pointer: `*Host` and its ArrayLists mutated from the plugin image
(`Host.zig:136-253`), `EditorAPI`'s 70 fn pointers returning slices into host memory,
`DocHandle.ptr`, immediate-mode `Surface.draw`/`drawDocument` into the host's live
`dvui.Window`, `RenderBridge` vertex/pixel buffers, allocator vtables, `settings.Access` on
plugin-owned values, `ServiceEntry.ptr` shared plugin-to-plugin, `core.FileTable` called with no
vtable. An out-of-process model means turning dvui's immediate mode into a command stream. That
is a different product; not recommended.

### 2.3 Hosting each plugin at its own URL? The store is ~80 % there.

Releases are keyed per `os-arch` in `ShardRelease.downloads` and sharded per fingerprint
(`app/store/registry/registry.zig:20-22, 70-114`), so `"web-wasm32"` is an additive key. On
wasm the store already browses `summary.json`/`releases.json` through `web_fetch`
(`PluginStore.zig:35, 1254-1259`; `web/index.html:307-325`); install is gated off
(`uninstalledCatalog` → `&.{}` at `:192`, `queueInstall` `:213`, `startDownload*` `:1538,1552`),
`compat.hostKey()` yields `"unknown-unknown"` on wasm (`registry/compat.zig:14-27`), and
`web_fetch.max_bytes` is 2 MB (`web_fetch.zig:29`) — too small for a plugin `.wasm`. Release
CI cross-compiles with `-Dtarget=`; `wasm32-freestanding` is a seventh entry, and
`plugin_sdk.install`'s `pluginExt` needs `.freestanding → "wasm"`.

### 2.4 Recommendation and order

1. **First: make static web bundling a one-liner for authors** (§2.5). It is the production-grade
   path today, the prerequisite for the "plugin app" the user wants, and it is how pixi gets a
   web build this month.
2. **Then: runtime wasm side modules as a `web-wasm32` store target.** The mechanism works; ship
   it behind the store so a bad wasm-ld build is "no web download for this release", not a broken
   web build. Steps and cost:
   - `sdk/plugin_sdk.zig create`: on wasm32 set `pic = true`, `entry = .disabled`,
     `single_threaded = true`, `link_libc = false`, name `{id}.wasm`; keep `export_symbol_names`.
     No fingerprint change. ~1 day.
   - `build/web.zig`: `import_table = true`, export `__stack_pointer`, add
     `FizzyWebPluginAlloc`-style exports; ReleaseFast/Small for the optimize class. ~½ day.
   - JS loader in `web/index.html` (~150-200 lines): growable `WebAssembly.Table` before
     `instantiateStreaming`; `fizzy_web_plugin_load(id, url)` → fetch → alloc `__memory_base` →
     `table.grow` for `__table_base` → instantiate with the 5 `env` globals →
     `__wasm_apply_data_relocs` → `table.grow(1); table.set(i, fn)` per `dylib_exports` entry →
     `FizzyWebPluginReady(id, idx[10])`. ~2 days.
   - `app/store/PluginLoader_web.zig`: a `WebDynLib` whose `lookup(T, name)` returns
     `@ptrFromInt(table_index)`; `loadAndRegister`'s sequence (`PluginLoader.zig:332-460`) runs
     unchanged; drop the wasm early-returns in `App.zig:942-958`; `Editor.loadUserPlugins`
     (`Editor.zig:588`) becomes async. ~3 days.
   - Store: `hostKey()` → `"web-wasm32"`; enable install on wasm via `web_fetch` (raise the cap or
     stream); in-memory installs, optionally Cache-API by `id@version@fingerprint`; enabled set
     in `localStorage` (settings.zon is in-memory on web, `Settings.zig:114`). ~3 days.
   - `plugin-build-action`: add the target. ~1 day.
   Realistic: 2–3 weeks plus a budgeted week for wasm-ld `-shared` surprises.
3. What "a flourishing web build" realistically is: **a per-plugin app, not a second full IDE.**
   The web has no project folder, no processes, no persistent config, and one thread, so the
   workbench-centric shell is permanently second-class there. A pixi-shaped or atlas-shaped app
   (one document type, mounts for files, download or Drive to save) is fully within reach, and a
   store of runtime wasm plugins then lets *that* app grow.

### 2.5 "Plugin app for free": how far it is, what is missing, proposed API

Native is already all the way there: `examples/minimal-app/build.zig` is 36 lines (`defer-app`,
`fizzy.buildApp(fizzy_dep, &.{ .{ .name, .module = dep.module("plugin") } })`,
`fizzy_dep.artifact(name)`); `plugin.create` exports the `"plugin"` module
(`plugin_sdk.zig` `PluginArtifact.static`) and `build/exe.zig:200-232` bundles it.

Missing, native:
- The plugin zon depends on `sdk/` only (by design). The app needs the fizzy **root** package, so
  the plugin needs a second `.lazy = true` dependency on it, resolved only by `zig build app`.
  (The lazy-dep-in-global-cache trap from CLAUDE.md applies: the plugin's `zig-pkg` grows a
  Velopack tree. Cosmetic.)
- A default shape. Add one shipped shape in the copy-don't-configure spirit,
  `app/layout/shapes/PluginApp.zig`: one region per distinct keyword set in `host.surfaces`
  (a plugin with `sidebar` + `main` surfaces gets a tray and a center; `main` only ⇒ minimal).
- Built-ins are bundled unconditionally (`build/exe.zig:170-179`) and `Editor` still holds
  `workbench: Workbench`. A `builtins:` list on `buildApp` follows the LIB_CHECKPOINT item that
  moves workbench state behind `Host`; do not gate the plugin-app on it.
- `build/package.zig` hardcodes `--packId fizzy` (`:105-106`), exe name (`:116-117`),
  `assets/windows/fizzy.ico` (`:149-150`), plist + `.icns` (`:160-166`), entitlements (`:177`).
  Parameterize from `AppInfo` (~1 day); a plugin-app can ship without installers first.

Missing, web (the real gap):
- `build/web.zig` is entirely fizzy-shaped: root `src/web_main.zig` (`:37`), six built-ins listed
  by hand (`:100-140`), `app_layout`/`app_plugins` never passed (`build/app.zig:324`), fixed
  export list (`:55-70`) and `index.html` template. **A consumer with `app-layout` set cannot
  compile the web exe at all**: `build_opts.has_app_layout` is true (`build/app.zig:197`) and
  `Editor.zig:3400` does `@import("app_layout")`, which the web graph never wires.
- `web`/`check-web` are `b.step` on fizzy's *dependency* builder (`build/web.zig:158,193`); Zig
  runs only the root package's steps, so `zig build web` in an example does not exist. Return a
  step/LazyPath the consumer hangs its own step on.
- `build/exe.zig:171-178` still special-cases "markdown null on wasm"; stale, harmless.

Proposed minimal API (all additive):

```zig
// plugins/<id>/build.zig
const created = fizzy.plugin.create(b, .{ .target = target, .optimize = optimize });
fizzy.plugin.install(b, created.lib, .{});
// needs `.fizzy_app = .{ .url = <fizzy root tarball>, .lazy = true }` in build.zig.zon
fizzy.plugin.app(b, created, .{
    .name = "pixi",                        // exe name, bundle id, config dir
    .layout = null,                        // null ⇒ shipped PluginApp shape; or b.path(...)
    .builtins = &.{ "workbench", "text" }, // later, once workbench leaves Editor
});
// registers `zig build app` (native exe) and `zig build web` (zig-out/web/), later `package`
```

Under it: `fizzy.buildWeb(fizzy_dep, plugins) -> *Step` beside `buildApp`, with `web.addSteps`
taking `app_name`, `app_layout`, `app_plugins`, `index_html`, `extra_exports`. About a week for
native + web without installers.

Wasm readiness of what exists: all six built-ins compile for wasm (`check-web` green). Out of
tree: **pixi** yes today via `buildApp` (30+ `wasm32` gates, in-memory zip, frame-sliced
packing, `web_file_io`; nobody has tried since the extraction — add a `check-web` step to its
CI); **zig** highlighting plausible (grammar is C, comes through dvui's tree-sitter option),
LSP never; **atlas** plausible with the plan in §4 (sqlite → in-memory backend on web, walk via
the mount layer, threads → frame-sliced); **ghostty** no, short of a WebSocket PTY backend
(`Pty.zig`'s per-OS switch is the seam).

## 3. Host findings (sdk/, app/, core/, src/, build/, bundled plugins)

### High

- **H1. The ABI fingerprint does not cover `Surface`** or `Host.Painter`/`Painter.Subject`,
  `Host.FileKind`, `Host.ServiceEntry`, `Plugin.PathEvent`, `EditorAPI.SaveDialogFilter`
  (`sdk/src/dylib.zig:86-169` lists boundary types; each of these is reached only through a
  slice/ArrayList, which `hashTypeShape` never follows, `fingerprint.zig:114-121`). The
  workbench dylib reads `Surface` fields off `regionMatching`'s slice
  (`plugins/workbench/src/Workspace.zig:114`). Adding a field to `Surface` today silently shifts
  the layout every installed plugin sees. Fix: list them, and add a comptime test that walks every
  `Host` container's element type and asserts membership.
- **H2. `Host.selections` keeps a borrowed id slice that `unregisterSurface` frees.**
  `setSelectionForKey` stores the registry entry's `s.id` (`Host.zig:1361-1367`); for document
  surfaces that slice is gpa-owned and freed in `Editor.unregisterDocSurface`
  (`Editor.zig:2171-2176`) right after `Host.unregisterSurface`, which leaves selections alone
  (`Host.zig:1102-1109`). Next `selectionForKey` compares freed memory. Same family:
  `orderedRemove` on a by-value `ArrayListUnmanaged(Surface)` (`Host.zig:243`) means every
  `*Surface` handed out this frame aliases the next entry after a close (the `tabs` slice in
  `Workspace.drawTabs`'s deferred `processTabsDrag`, `Workspace.zig:330-333`). Fix: intern
  selection ids as `State.internName` already does, drop selections naming a removed id, and give
  `Surface` stable storage (pool/segmented list).
- **H3. Live unload can leave function pointers into an unmapped image.**
  `Editor.unloadPlugin` (`Editor.zig:1379-1432`) unregisters, `deinit`s, `lib.close()`. Not
  swept: dvui `dataSetDeinitFunction` entries (text's `TextEntryWidget` sets one), open
  dialogs/toasts whose `displayFn` lives in the image (`core.dialogs.dialog` is compiled into
  every image; `Host.requestNewDocument` invokes it from whichever image called,
  `Host.zig:1488-1503`), queued dialog-result callbacks (`Editor.zig:3125`),
  `Host.pending_new_document_owner` (not cleared in `unregisterPlugin`, `Host.zig:738-773`), and
  mounts (`Host.mount`, `Host.zig:563`, has no owner, so `FileTable` keeps a `vfs.Fs` vtable into
  freed code). The exit path already avoids `dlclose` for the data-store hazard
  (`Editor.zig:690-706`); the live path does not. Fix: owner-scoped sweep in `unregisterPlugin`
  (give `mount` an owner), refuse unload while an image-owned dialog is open, document
  `dataRemove` obligations in `deinit`.
- **H4. Partial registration + `err_register` leaves dangling contributions, then closes the
  image.** Bundled `register`s call `registerPlugin` first, then several `try host.register*`
  (`plugins/image/plugin.zig:66-70`). A later failure returns `err_register`
  (`dylib.zig:380-387`); `loadAndRegister` maps it to `RegisterRejected` and `errdefer
  lib.close()` (`PluginLoader.zig:358, 435-441`) while `Host.plugins`/`surfaces`/`services`
  still point into it. Fix: on any non-ok status `unregisterPlugin(pluginById(expected_id))`
  before closing; better, `exportEntry.register` does it plugin-side too.
- **H5. Store install joins the registry's plugin id into filesystem paths unvalidated.**
  `PluginStore.buildJob` (`:1581-1590`) joins `<config>/plugins/<id>/<id>.<ext>` with `id` from
  the catalog; `uninstallPlugin` `deleteTree`s `<config>/plugins/<id>` (`Editor.zig:1495-1499`).
  `App.isValidPluginId` (`App.zig:353`) guards disk discovery but not the catalog path, and
  `FIZZY_PLUGIN_REGISTRY_URL` (`PluginStore.zig:774-784`) makes the registry user-suppliable.
  SHA-256 verification itself is sound. Fix: validate ids when the summary/shard is parsed and
  again in `buildJob`/`applyUninstall`; bound download bodies (`download.zig:50-56` and
  `fetchJson` are unlimited).
- **H6. `@errorName` on errors returned across the dylib boundary**, against the rule written at
  `Editor.zig:4199-4203`: `Editor.zig:1277, 3116, 3447, 3457, 3568, 4526, 4614, 4620`,
  `Keybinds.zig:940`, and inside the SDK `Plugin.zig:497-498`, `Host.zig:1468-1470`. Logs print
  a wrong error name. Fix: normalize in the `Plugin` wrappers (`error.PluginFailed`) or the
  shared SDK error enum the checkpoint proposes.

### Medium

- **H7. `EditorAPI`/`Host` still carry pixi- and workbench-specific members**: `paletteFolder`
  (fizzy creates `<config>/palettes` for every app, `Editor.zig:317, 524-530`), `explorerRect`/
  `explorerVirtualSize`/`explorerViewportWidth`/`explorerBranchIsOpen`/`setExplorerBranchOpen`/
  `setExplorerNewFilePath`/`drawWorkspaces`, `panZoomScheme`, `NewDocGrid` on `createDocument`
  (`Host.zig:1593-1595` admits it), the quit/save cluster (`setPendingCloseDocId`,
  `queueCloseAfterSave`, `trackQuitSaveInFlight`, `resumeSaveAllQuit`, `abortSaveAllQuit`,
  `cancelPendingSaveDialog`, `requestWebSave`; `EditorAPI.zig:55-81, 211-215, 232-248`), and
  `sdk.pane_layout` (26 lines that exist for pixi's takeover surface). Fix: explorer* → the
  `workbench` service or region context; `paletteFolder` → `pluginInstallDir`; `NewDocGrid` → an
  opaque plugin-defined blob; quit flow behind a versioned `save_flow` service or host-private.
- **H8. The SDK `Host` draws a dialog.** `showNewDocumentChooser`/`newDocumentChooserDisplay`/
  `newDocumentChooserButton` (`Host.zig:1473-1586`) is a dvui dialog compiled into every plugin
  image, with its `displayFn` in whichever image called `requestNewDocument`. Move behind an
  `EditorAPI` hook.
- **H9. The plugin vtable is wider than the contract needs** (~60 hooks, `Plugin.zig:72-305`).
  The staging protocol takes eight where `open(path, grouping) !*anyopaque` would do;
  `bindDocumentToPane(canvas_id, workspace_handle, center)` / `removeCanvasPane` leak workbench
  concepts; `saveDocumentAs(..., *dvui.Window)`. Zero host call sites: `contributeMenu`,
  `documentHasNativeExtension`, `documentByPath`. The simplest viewer needs 28 entries
  (`plugins/image/plugin.zig:27-55`). Delete the dead three now; collapse the staging protocol
  while the fingerprint is free.
- **H10. Two keybinding mechanisms; dispatched keys are never marked handled.** Commands +
  `Keymap` (`Keybinds.zig:893-948`) coexist with `Plugin.VTable.tickKeybinds` per-frame
  self-matching (`Editor.zig:3440-3449`); the keymap path leaves the event unhandled
  (`Keybinds.zig:914-920, 933-936`) so the focused widget sees it too — the clipboard
  double-fire. pixi writes `win.keybinds` with `win.gpa` directly (`pixi/plugin.zig:872-903`)
  because plugins cannot register into `app/keymap`. Fix: one path — plugins register `Command`s
  with default chords, the host dispatches and marks handled; drop `tickKeybinds`.
- **H11. Duplicated build glue.** Four near-identical `plugins/*/static/integration.zig`;
  `plugins/shared/build/helpers.zig` hand-mirrors `sdk/plugin_sdk.zig` (`dylib_exports`,
  `plugin_options_import`, `readManifestAt`, `generatedDylibRoot`); `build/exe.zig:39-58`
  repeats the install chain per plugin; `build/app.zig:198-215` exposes `static_workbench/text/
  image` but no `static_markdown` while `App.bundledDylibEnabled` reads `static_<id>` generically
  (`App.zig:976-991`). Fix: `helpers.integration(comptime id, .{…})` and one comptime list
  driving exe/web/app. Also `helpers.zig:51` relative-imports `../../../sdk/src/
  manifest_identity.zig`, the one-module trap CLAUDE.md forbids; `sdk/manifest_identity.zig`
  exists for this.
- **H12. Dead, dangerous helpers in `sdk/src/menu.zig`**: `menuItem`/`menuItemWithChevron`/
  `submenu` have no callers and call `dvui.menuItem` directly (the per-dylib `MenuWidget` crash
  `EditorAPI.drawMenuItem` warns about, `EditorAPI.zig:269-278`) and `dvui.icon`. Delete;
  `menu.zig` vs `menus.zig` is a naming trap.
- **H13. `wikilink` service type lives in the SDK and in the fingerprint**
  (`sdk/src/services/wikilink.zig`, 424 lines, listed at `dylib.zig:150-157`), so a change to one
  plugin pair's API bumps the fingerprint for everyone, against "services are versioned, not
  fingerprinted" (`Host.zig:997-1003`). Move it to the producing plugin's package; consumers
  pin it; rely on `service_version`.
- **H14. Silent fallback hides a broken bundled dylib.** `postInit` does `loadBundledDylib(...)
  catch { try m.register(host) }` with no log (`Editor.zig:1594-1600`); the comment says none of
  the bundled plugins ship as dylibs, but `zig-out/arm64-macos/plugins/{image,markdown,text,
  workbench}` exist. Log the error; fix the comment.
- **H15. `readPluginReservedField` re-parses all of `settings.zon` three times per field per
  plugin** (`App.zig:671-682`), per plugin from `seedPluginFlags`/`reconcilePluginEnabled` and
  per directory entry in `reconcileDiscoveredPlugins` (`Editor.zig:2925`) on every watcher
  event. Parse once (Zoir) and walk.
- **H16. User plugin load order is filesystem iteration order** (`Editor.zig:614`) ⇒
  registration order ⇒ surface/menu/tab order varies by OS. Sort ids.
- **H17. `waitForPluginSaves` busy-spins the GUI thread** (`App.zig:966-970`); use the futex
  pattern `cancelPluginLoadingJobs` already uses (`Editor.zig:1334-1377`).
- **H18. No test covers unload, hot reload, or store install.** `tests/integration.zig` has 60+
  tests, none touching `unloadPlugin`, `reconcileChangedPluginBinaries`, or a dylib load. A
  headless test that loads `examples/hello-plugin`'s dylib, draws, unloads, draws again would
  catch H2–H4.

- **Native menu**: `NativeMenuItem` parents only to fizzy ids or a plugin's own contribution

  generated view) cannot be a tab; ownership is by extension only.

## 5. zig-drive and the cloud-fs layer

### 5.1 Correctness (ranked)

- **D1. A Drive listing in flight panics when another op forgets its directory.**
  `drive.zig:425` `forgetChildren(job.path)` runs synchronously in `start`; `:503` and `:568`
  do `index.get(job.listing).?`. Any mutation → `FileTable.invalidateAll` → the tree re-lists
  `/` → `/Notes` (still listing) is dropped → its response lands on `.?` null — UB in the
  ReleaseFast web build. Fix: refresh a listing in place (update keys, remove only names absent
  after the last page); replace every `.?` on `job.listing`/`job.path` with `orelse
  error.NotFound` + re-resolve.
- **D2. `Client.cancel` during `pump` delivery is a use-after-free.** `drive.zig:199-218`: `pump`
  takes the ready list and delivers one at a time; a callback that cancels a *later* job in the
  same batch destroys it, then the loop delivers on freed memory. Reachable today:
  `FileTable.Mutation.onDone` (`FileTable.zig:833`) → `invalidateAll` → `IndexJob.cancel`
  (`:618-628`) while a search runs on Drive. The `Fs.zig:101` contract ("its callback will not
  run") is also violated by `Mem`, `LocalFs` and both transports for a job already taken by
  `pump`. Fix: a `delivering` set in `http.Completions`; `cancel` of a taken id marks it skipped.
- **D3. Refresh-failure request storm.** `plugins/drive/plugin.zig:194-196` re-arms every frame
  while `mounted and pending == null and now > expires_at - 120s`; `fail` (`:416`) does not sign
  out when mounted and `expires_at_ms` never moves → one token POST per frame (on web, one GIS
  `requestAccessToken` per frame, popup-blocked outside a gesture). Fix: exponential backoff on
  `expires_at_ms`; a 400/401 refresh while mounted → `signOut`.
- **D4. A failing mount listing is re-asked every frame, silently** (`FileTable.zig:376-395`,
  `ListJob.onListed:423` `result catch return`). Nothing in fizzy handles `error.Unauthorized`.
  Fix: install an empty listing with a TTL on error, log once, add `Env.failed(path, err)` so the
  drive plugin can refresh + `invalidateListing`.
- **D5. Quit save-all discards edits when a mount write fails** (`Editor.zig:3927-3936` closes
  once `docSaving` clears regardless of outcome; `MountIo.Save.onWritten` `:188-196` leaves the
  doc dirty while the app exits). Re-check `isDirty` and `abortSaveAllQuit`.
- **D6. Edits made during a slow upload are marked clean.** `text/src/Document.zig:371-382`
  sets `clean_op_id = topOpId()` at *completion*; `saveThroughMount` swallows `SaveInProgress`
  (`Editor.zig:4566`). Type, ⌘S (2 s upload), keep typing → clean tab → quit without prompt.
  Fix: `savedBytes` records the op id and `written` restores that; MountIo re-saves after
  `SaveInProgress`.
- **D7. Save As / new file onto a mount fails `NotFound`**: `MountIo.zig:155` only calls
  `writeFile`; `Mem.writeImpl` (`mem.zig:169`) and Drive `.write` (`drive.zig:436`) require the
  node, `LocalFs.writeFile` creates. Define `writeFile` as create-or-replace.
- **D8. `unmount` never reaches `MountIo`**: `FileTable.unmount` (`:237-256`) cancels only its
  ListJobs; sign out mid-open leaves `loads[path]` forever; mid-save leaves `docSaving` true →
  quit hangs. Add `Env.unmounted(prefix)`.
- **D9. `NativeTransport.cancel` joins a blocking fetch on the UI thread**
  (`NativeTransport.zig:198`; `std.http.Client.fetch` has no timeout) — clearing the search box,
  sign-out, unmount and quit all stall for a round trip or forever. Transfer ownership to the
  worker. Also `:156` reads `self.wake` after unlocking while `deinit` (`:77-83`) does not join.
- **D10. Loopback `stop()` double-closes the socket; the listener is one-shot; no deadline**
  (`oauth.zig:188, 239-245`). Chrome's speculative idle connection can consume the single
  `accept`; `.awaiting_code` + `needsContinuousRepaint` burns CPU until Disconnect. Loop until a
  request carrying `state` (404 the rest) or 5 min; `sdk.refresh()` from the thread.
- **D11. zip reader: 32-bit offset arithmetic overflows on wasm32** (`zip.zig:46-48`
  `data_off + hdr.compressed_size`, `:174`): a crafted `compressed_size` wraps below `data_off`,
  the bounds check passes, the inflater reads past the archive. No archive-wide inflate budget
  (`:193` trusts `uncompressed_size` up to 4 GiB; a zip bomb OOMs the tab). Compute in `u64`,
  cap total inflate. Path traversal, `__MACOSX`, absolute names, zip64 and encryption are
  handled correctly; CRC32 unchecked.
- **D12. `Mem.rename("/a", "/a/b")` orphans the subtree** (`mem.zig:193-218`). Refuse.
- **D13. `FileTable.isDir` on a mount root is false** (`:857-866`; `exists` special-cases it at
  `:845`) → a drop onto `zip://demo` treats it as a file.
- **D14. Windows joins unaudited**: `std.fs.path.join` on possibly-mounted paths in
  `FilesService.move` and `workbench/src/files.zig:512, 514, 764, 1288, 1311` produce
  `gdrive://me\Notes\x`. Add a mount-aware `core.paths.join`.
- **D15. In-call `pump()` on a mount delivers *every* completion mid-draw** (`FileTable.zig:393`,
  `MountIo.zig:79,156`, mutations `:775-811`): document opens/closes/writes run inside the tree
  widget, against the header's "once per frame before anything draws". Pump inline only for the
  disk, or add `Fs.pumpJob(job)`.
- **D16. Web GIS callback runs outside the frame** (`plugin.zig:465-472`). Park the token, apply
  in `beginFrame`.
- **D17. Two archives with one stem share a prefix** (`archive/src/Document.zig:29`;
  `FileTable.mount:222-227` replaces in place) → closing one unmounts the other. Uniquify.

### 5.2 Security

- Refresh token and desktop client secret in plaintext `settings.zon`, shown unmasked in the
  settings pane (`drive/src/Settings.zig:15-33`, `plugin.zig:426-436`), default file perms.
  Google treats an installed-app secret as non-confidential (Settings.zig says so;
  CLOUD_FS_PLAN does not). The refresh token is a real credential; `drive.file` limits blast
  radius. In order: `settings.Value` `.secret = true` (masked, excluded from export);
  `chmod 0600` when a secret is present; a `Host.secrets` seam (`get/set(key)`) with
  keychain/libsecret/DPAPI backends and settings.zon fallback — design the seam now.
- PKCE verifier/state from the OS CSPRNG, loopback on `127.0.0.1:0`, `state` checked — good.
- Header injection: `Name: value\n` lines (`WebTransport.zig:66-73`, `index.html:242-245`); a
  CR/LF either injects or makes `Headers.append` throw synchronously inside the wasm import (no
  try/catch at `:241-247`) and traps the frame. Reject CR/LF/`:` in Zig; try/catch in JS.
- TLS: `std.http.Client` verifies against the system bundle. No request timeout anywhere (D9).
- Web GIS silent re-request from `beginFrame` is not a gesture → blocked when consent is not
  cached → nothing recovers (D3/D4).

### 5.3 Design points

- The async `Fs` shape fits: nobody blocks, the disk completes in-call, the web spins nothing.
  The gaps are around it: no error channel from `FileTable` to the mounting plugin (the
  `Unauthorized → refresh → retry` in `Fs.zig:32` is implemented nowhere), no single-job pump,
  walkers return partial results silently on a slow mount.
- **`drive.file` scope reality** (`oauth.zig:12`): `files.list` returns only files this app
  created or the user picked — a fresh sign-in shows an *empty* My Drive and `root_folder_id`
  does not help. Either add Google Picker (trivial on web; none on native → needs
  `drive.readonly`/`drive` + verification) or document the empty tree. This is the largest gap
  between "built" and "usable".
- Cross-mount rename: refusing is right; a `FileTable.copyTree` chain over the same primitives
  gives disk↔drive drag, which users will try first.
- No watcher: `changes.list` with a start token polled every few seconds → `Client.forget` +
  `FileTable.invalidateListing`/`noteFileModified`. Zip mounts need nothing.
- Last write wins: no ETag precondition in Drive v3, but `modifiedTime`/`version` are in every
  listing; GET metadata before PATCH, refuse on change, reuse the DocumentWatcher conflict UI.
- Owner migration (pixi/atlas): implement `documentBytes`/`documentWritten` (pixi already
  serializes for the web download), then have the host prefer the bytes hooks *for the disk
  too* so `saveDocument` becomes legacy and every owner has one path.
- Second backend: Google-specific in `drive.zig` = URL shapes, `parents`/duplicate-name
  semantics (hence the path index), `trashed`, `google_app` mime, page tokens, RFC3339, 401/403
  mapping; generic = the Job state machine, `Completions`, query escaping. Dropbox/OneDrive are
  natively path-addressed, so the index stays Drive-only. Move `oauth.zig` (PKCE, loopback,
  exchange/refresh) out of `plugins/drive` before backend #2 — they need the identical flow.
- Layering: `core.vfs` re-exporting a dependency-free wasm-safe package is the `zf` shape —
  fine. `drive.zig` (Google REST) does not belong under core: split into `zig-vfs` (core dep:
  Fs, Mem, zip, `http.Transport`) and `zig-gdrive` (dep of `plugins/drive` only). **The path pins
  (`build.zig.zon:66`, `sdk/build.zig.zon:47`) point outside the repo, so a fresh clone or CI
  cannot build fizzy at all** — URL-pin now.
- Perf: one `std.http.Client` per request (`NativeTransport.zig:161`) = CA rescan + TLS
  handshake per `files.list`. Share one client.
